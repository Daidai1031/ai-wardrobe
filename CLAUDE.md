# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev      # start dev server (Next.js, http://localhost:3000)
npm run build    # production build
npm run start    # run production build
npm run lint     # ESLint CLI (Next 16 removed `next lint`)
```

There is no test suite configured. There is no single-test command.

## Architecture

Next.js 16 App Router app ("ai-wardrobe") using Server Components + Route Handlers, Supabase (auth/DB/storage), Claude Vision for classification, and fal.ai for background removal. It replaces an earlier Python prototype — this is a from-scratch rewrite, not an upgrade.

### Route groups

- `src/app/(auth)/` — `login`, `signup` pages, unauthenticated.
- `src/app/(dashboard)/` — the main app: `home`, `plan`, `closet`, `closet/[id]`, `outfits`, `stylist`, `analytics`, `profile`, `travel`, `travel/[id]`, plus `pro` / `pro/[clientId]` (the human stylist's console — see "The human stylist console" below). Protected by `src/proxy.ts`.
- `src/app/(print)/` — pages that must render without the dashboard sidebar and chrome. Only `travel/[id]/print` so far; it is its own route group rather than a `print:hidden` sidebar so the chrome is absent from the tree instead of merely invisible.
- `src/app/trip/[token]/` — the **public** read-only shared trip page. Top-level and outside every group, since it has no session at all; see "Travel mode".
- `src/app/api/ai/` — server-side AI pipeline endpoints: `classify`, `convert`, `stylist`, `daily`, `weekly`, `item-outfits`; `src/app/api/weather/` proxies OpenWeatherMap; `src/app/api/geocode/` resolves a city name to coordinates (see "Weather & geocoding" below).
- `src/app/api/google/` — `auth` and `callback` implement Calendar OAuth (see "Google Calendar OAuth" below).
- `src/app/api/keep-alive/` — a Vercel Cron target (schedule in `vercel.json`, every 3 days) that runs a trivial `select id from profiles limit 1` and returns an empty `200`, purely to keep the free-tier Supabase project from being paused after ~7 days of inactivity. Not part of any user flow; no auth (runs as anon under RLS, which is fine — the query still counts as DB activity). See README's "Keeping Supabase awake" for details.

### Auth & routing

`src/proxy.ts` is this Next.js 16 project's `middleware.ts` equivalent — Next 16 renamed the convention (`middleware()` → default-exported `proxy()`, `config` → `proxyConfig`). It refreshes the Supabase session on every request, redirects unauthenticated users away from dashboard routes (`/home`, `/plan`, `/closet`, `/outfits`, `/stylist`, `/profile`, `/analytics`, `/travel`, `/pro`), and redirects authenticated users away from `/login`/`/signup`. When adding a new protected top-level route, add its path prefix to the `isDashboard` check here. `/trip/[token]` is deliberately **not** in that list — it is the public shared-trip page and its token is the whole credential.

Three Supabase client factories exist and are not interchangeable:
- `src/lib/supabase/client.ts` — browser client, for use in Client Components.
- `src/lib/supabase/server.ts` — server client bound to Next's `cookies()`, for use in Server Components / Route Handlers.
- `src/lib/supabase/service.ts` — service-role client that bypasses RLS entirely. Only for tables with no client-facing policy by design (`google_connections`), for global reads a session can't have (stylist booking availability), and for the stylist-side writes and occasion projection in `src/lib/stylist/`; never import it into a Client Component.

### Weather & geocoding

`src/lib/weather/` is a provider abstraction (ROADMAP Phase 6.0-E / decision D2), split so the providers only ever deal in coordinates:

- `types.ts` — shared `WeatherData`/`DailyForecast`/`GeoPoint` types and the `WeatherProvider` contract (`current(lat, lon)`, `forecast(lat, lon, days)`).
- `openweather.ts` — `getCurrentWeather(lat, lon)`, used by `/api/ai/daily` (unchanged behavior, D2).
- `open-meteo.ts` — `getForecast(lat, lon, days)`, used by weekly planning (6.2) and later travel (6.3). Also exports `getForecastAsCurrent(lat, lon, date, city)`, which expresses one forecast day in the `WeatherData` shape a plan stores and renders, so a plan generated for a date that isn't today reasons about *that* day's weather; and `describeWeatherCode()` for the WMO scale. No API key; free tier is non-commercial + CC BY 4.0 attribution, see D2 for the commercial exit.
- `geocode.ts` — `geocodeCity(city)`, the **only** place a city name becomes coordinates. Neither provider above knows what a city is.

Coordinates are geocoded once and cached on the row, not re-derived per weather call — geocoding on every fetch would be a wasted external request per daily/weekly/travel generation for a city that never moves. The cached location sources:
- `profiles.city` → `profiles.lat`/`lng`, geocoded in `profile-form.tsx`'s `handleSave()` only when the city text actually changed (via `GET /api/geocode?city=`), then saved in the same `profiles` update.
- `travel_plans.destination` → `destination_lat`/`destination_lng`, copied at trip-resolve time from the coordinates the trip's own calendar events already carry (see "Travel mode"). Nothing re-geocodes a destination: the events reaching `detectTrips` were enriched by Calendar sync, so the coordinates are already on the row.
- `calendar_events.location` → `weather_city`/`weather_lat`/`weather_lng`/`weather_timezone`, enriched during Calendar sync. `classifyEvents()` conservatively extracts an explicit city from the already-shared location string, and `geocodeCity()` resolves each distinct city once. `weather_location_resolved` prevents locationless/online events from being retried forever and is reset when Google changes the raw location. From `/plan`, the event address is clickable: `PATCH /api/calendar/events/[id]/location` geocodes and stores a planning-only `location_override` plus override coordinates. Override fields stay separate from Google's raw location because the OAuth grant is read-only and a later sync must not erase a user's correction; clearing the override restores Google's location.

`src/lib/weather/calendar-location.ts` chooses **all** weather coordinates that matter per plan date, preferring the user's event override over the automatically enriched Calendar city. Multiple same-day cities are preserved rather than collapsed to the profile. An ordinary/vacation multi-day event uses its destination on every overlapping day; a multi-day business/work trip additionally includes the profile home city on its first and last local dates, representing departure and return. Daily and weekly both pass every location's conditions to Claude and render every city in the UI. The rule engine only applies its “too hot for sleeves” deletion when every city on that date is hot, leaving the model removable layers for mixed climates.

Travel titles can carry the only explicit destination. `explicitTravelDestinationFromTitle()` deterministically handles forms such as `Vacation: Hamptons`, `Business Trip (London)`, and `Work trip to Chicago`; Calendar sync backfills these even for rows whose older location-only classification had already been marked resolved. `geocodeCity()` maps the colloquial Hamptons region to a representative East Hampton, New York coordinate while preserving the label “Hamptons.”

`GET /api/weather` is a standalone ad-hoc lookup endpoint (not on the daily/weekly/travel hot path) — it accepts either `lat`/`lon` directly or a `city` param that it geocodes per-request for convenience; that per-request geocode is fine there specifically because the endpoint isn't called repeatedly for the same city, unlike the cached paths above.

### Google Calendar OAuth

ROADMAP 6.0-A / decision D1. This is deliberately its own OAuth flow, separate from the Supabase Google *login* provider — Supabase only hands back `provider_refresh_token` once, at initial sign-in, and doesn't persist it, which isn't workable for a long-lived Calendar connection. Calendar and Gmail are (and will remain) two independent consent grants, not one combined "Connect Google" button — see D1's reasoning: `gmail.readonly` is a restricted scope that requires a paid CASA review once the app leaves Testing mode, and bundling it with Calendar would mean a user declining Gmail also loses Calendar. Only the Calendar leg is implemented so far; Gmail is a deliberately separate future task and shares nothing with this code path yet beyond the same `google_connections` table.

- `GET /api/google/auth?scope=calendar` — the only accepted `scope` value right now (anything else 400s). Requires an existing Supabase session; generates a CSRF `state`, stashes it in an httpOnly cookie scoped to `/api/google`, and redirects to Google's consent screen requesting `calendar.readonly` with `access_type=offline&prompt=consent` (forces a `refresh_token` back on every authorization, not just the first).
- `GET /api/google/callback` — validates `state` against the cookie, exchanges `code` for tokens, and upserts `google_connections` (one row per user; access/refresh token, `expires_at`, and the actual granted `scopes` array from Google's response — never assumed from what was requested). Redirects to `/profile?google_calendar=connected|error`, which the Connected accounts section reads.
- `POST /api/google/disconnect` — revokes at Google, then deletes the row. POST, not GET, so a prefetch can't revoke someone's access, and the user id comes from the session so it can only ever disconnect the caller. The local row is deleted **even if Google's revoke call fails** — the user asked to disconnect and keeping tokens we've been told to forget is worse — so the UI says so explicitly rather than implying the grant is always cleared on Google's side too.
- `src/app/(dashboard)/profile/google-connections.tsx` — the settings UI. Status is read **server-side** in `page.tsx` via `getConnectionStatus()`: `google_connections` has RLS with no policy so a browser client can't query it at all, and `GoogleConnectionStatus` deliberately carries no tokens, since passing them through a Server Component's props would defeat the same guarantee. Three states matter: not connected, connected, and `needsReconnect` (a row exists but `invalid_at` is set) — the last is routine under Testing mode's ~7 day refresh token expiry, not an exception. Calendar and Gmail render as **separate** rows per D1; the Gmail row is shown as unavailable rather than hidden so the two-grant design is visible in the UI, matching `?scope=gmail` still returning 400.
- `src/lib/google/client.ts` — the only code that touches Google's OAuth endpoints or `google_connections` directly:
  - `getAccessToken(userId)` — the one function calendar-fetching code (Phase 6.1+) should call. Returns a valid access token, transparently refreshing if expired; returns `null` (never throws) if there's no connection, it was already marked invalid, or the refresh itself fails. A failed refresh sets `google_connections.invalid_at` so the caller can prompt for reconnection instead of retrying every call — this matters because Testing-mode refresh tokens expire after ~7 days (see README's Google Calendar OAuth setup section) until the Cloud project passes verification.
  - `hasScope(userId, scope)` — gate any Calendar-dependent UI/route on this before assuming the feature is usable.
  - Both read/write through `createServiceSupabase()` (`src/lib/supabase/service.ts`), since `google_connections` has RLS enabled with no policy — tokens are never reachable from a user's own session, by design.

### Calendar event sync, semantic enrichment, and local-day bucketing

ROADMAP 6.0-C. Three separable pieces:

- `src/lib/google/calendar.ts` — `listCalendarEvents(accessToken, timeMin, timeMax)`, a thin wrapper around Google Calendar v3 `events.list` on the primary calendar (`singleEvents=true` so recurring events arrive pre-expanded). Knows nothing about our DB or auth; callers supply an already-valid access token from `getAccessToken()`.
- `GET /api/google/calendar/sync?timeMin=&timeMax=` (`src/app/api/google/calendar/sync/route.ts`) — the orchestrator: checks `hasScope`, gets a token, fetches events, upserts the raw fields (title/location/starts_at/ends_at/all_day/attendee_count) into `calendar_events` via the normal session-scoped `createServerSupabase()` client (this table has an ordinary `auth.uid() = user_id` RLS policy, unlike `google_connections` — no service role needed here). Defaults to `[start of today UTC, +14 days]` when no range is given. **Nothing triggers this automatically** — no cron, and neither `/api/ai/daily` nor `/api/ai/weekly` calls it. They read whatever `calendar_events` already holds, so an un-synced account plans as if the calendar were empty, with no error anywhere. `/plan`'s "Sync calendar" button is the only UI entry point; it exists because the failure mode is silent and reads as "the calendar integration is broken" rather than "nobody has pulled it since the last time". A scheduled sync is still not built.
- `src/lib/calendar/classify-events.ts` — `classifyEvents()`, one batched Haiku call that takes every event still missing `occasion`/`formality` and returns both per event. The sync route only ever passes rows where `occasion IS NULL`, so a given `google_event_id` gets classified exactly once no matter how many times sync reruns — this is the cost lever ROADMAP 6.0-C calls out (batch weekly, not per-event). Deliberately fed only title/location/attendee_count, never the event's `description` — a user's own manual notes on an event (e.g. an expected-answer key for testing this pipeline) must never leak into the classification input.
- `src/lib/calendar/day-bucket.ts` — `eventsOnLocalDay(events, localDate, timeZone)`, the single function daily (6.1) and weekly (6.2) planning both call to answer "what's on the calendar for this local day," instead of each re-deriving it. Two things it handles that are easy to get wrong once, let alone twice: an event's UTC instant near a day boundary must convert through the location's IANA `timeZone` to land on the correct local day (naive UTC-date slicing is wrong), and a multi-day event must appear on every local day its interval overlaps, not just the day it starts. All-day events are handled as a special case of both: Google's all-day dates are timezone-agnostic calendar dates with no real instant, encoded by the sync route as `<date>T00:00:00Z` purely to fit the `timestamptz` column, so `eventsOnLocalDay` compares those by raw UTC date-string components and skips timezone conversion for them entirely — running an all-day event through `timeZone` conversion would incorrectly shift it onto the adjacent local day in any non-UTC zone. **Verified 2026-07-30** against 8 real events synced from a live Google Calendar spanning 7/30–8/7: confirmed three same-day events (9:45am, 3pm, and 8:15pm local) all correctly bucket onto the same `America/New_York` local day despite the 8:15pm one crossing into the next UTC calendar date; confirmed a 2-day all-day trip appears on both of its local days and not the exclusive end date; confirmed bucketing genuinely shifts under a different `timeZone` (`Asia/Shanghai`) rather than being hardcoded to one zone.
- `GET /api/ai/daily` now calls `eventsOnLocalDay` before building its dynamic segment prompt. There is still no "current week" boundary anywhere — `/api/google/calendar/sync`'s window is caller-specified, not tied to a Mon–Sun week; that's a Phase 6.2 concern.
- `POST /api/ai/daily` has two modes. Without `segmentId` it rebuilds the whole day (the original Dislike path). **With `segmentId` it regenerates only that segment** — rerunning the whole plan to fix one bad look discarded the segments the user was happy with and paid for a full generation. The single-segment prompt gets the whole day as context and returns both the new segment and `nextChangeFromPrevious`: the following segment's "what changed" line describes the transition from the segment being replaced, so leaving it alone would point at an outfit that no longer exists. Getting it in the same call keeps it accurate at no extra cost. Only the target segment's own items are excluded — items in the segments being kept stay available, since wearing the same blazer through two parts of a day is normal. Weather is read from the stored plan rather than refetched, so the regenerated segment reasons about the same conditions as the rest of the plan.
- Two things about `/api/ai/daily` that are easy to trip over. **Timezone**: it resolves as `?timezone=` → `profiles.timezone` → `"UTC"`, and the `/home` client passes neither `?timezone=` nor `?date=` — so a user who never set a timezone silently plans in UTC, which lands events near a day boundary on the wrong local day without any error. Both query params exist and are useful for testing a specific day from the browser. **Weather** is snapshotted into `outfit_plans.weather` at generation time and is not refreshed for the rest of that local day; changing the profile city or syncing a new event city does not rewrite an already-generated outfit, only a full day/week regeneration does. Single-segment redo intentionally reuses the plan snapshot so one look cannot reason about different weather than the rest of its day.

### Weekly planning

ROADMAP 6.2. `/plan` plans seven days from today in one call, because the constraints that justify weekly planning at all — a statement piece not repeating inside the window, ≥2 days between wearings of a basic, no close-to-skin item on consecutive days, covering the week's full formality range — are things no per-day generation can know.

**A date has exactly one plan.** `outfit_plans_cache_key` is `(user_id, plan_date, travel_plan_id)`; `source` was deliberately removed from it in 6.2. Keying on `source` let one date carry both a `daily` and a `weekly` row — two independent generations with different inputs, showing the user different outfits for the same Thursday on `/home` and `/plan` with nothing syncing them. `source` is now provenance only: `/home` reads today's plan whatever produced it and badges it "From your week plan", and redoing one day flips it back to `daily` because that day is no longer bound by the week's constraints (`/plan` badges those "Adjusted").

- `src/lib/planning/plans.ts` — `readPlansForDates()` / `readPlanForDate()` / `hydrateSegments()`. Daily reads one date and weekly seven, but the joining, ordering and layout-carrying are identical, so both go through here. Nothing in it filters on `source`.
- `src/lib/planning/candidates.ts` — `selectCandidates()`, decision D8's hard filter. Temperature and formality bounds come from the week itself, so a 28°C week never offers coats. Its real risk is over-filtering into uselessness, so it relaxes in stages (season **and** occasion → either → no filter) and guarantees a per-category minimum, rather than trusting one pass. Untagged items always pass — missing data must never exclude an item, and `pinnedIds` bypasses both the occasion filter and the ranking for items some segment has no valid answer without (see the sport rule below). Two things keep it from handing the model the same forty pieces forever: `recentlyPlannedIds` (what the surrounding days already use) costs 2 points, and `variety` adds up to 1.5 points of noise per item. The scoring is otherwise fully deterministic, so the same closet produced the identical top 45 on every run and the model — reasonably — kept picking the same standouts out of it; regenerating is supposed to give you something else. `last_worn_at` alone can't do this job: it only moves when a day is confirmed **worn**, which most days aren't.
- `GET /api/ai/weekly` is **read-only and never calls Claude**, unlike `/api/ai/daily` which generates on a cache miss. A daily pick is one small call the user expects automatically; a week is a large call over the whole wardrobe, so opening `/plan` shows the forecast, calendar and whatever is already planned, and generating is a deliberate button press.
- `POST /api/ai/weekly` generates, persisting through `replace_weekly_plans` — one transaction, because a partial week doesn't satisfy the cross-day constraints that were the point. Days already `status='worn'` are skipped, never overwritten, and come back in `skippedDates` so a day left alone doesn't read as a silent failure.
- Any day in the window is editable from `/plan`, not just today: per-segment redo, the shared Canvas editor, and save-to-Looks all work on the selected day. The backing routes and RPCs were never date-limited — only the UI was, which is why the day panel used to offer nothing but a link to `/home` (which always shows today). `src/components/outfit/segment-canvas-editor.tsx` is the shared editor `/home` and `/plan` both mount. The "Open on Home" link now appears only when the selected day *is* today.
- Per-day redo goes through `POST /api/ai/daily?date=`, not a weekly endpoint — that route already handles one date and already flips `source` correctly. Its weather resolution had to grow up for this: `weatherForDate()` uses OpenWeather current conditions only when the date *is* today and `getForecastAsCurrent()` (Open-Meteo) otherwise, since reasoning about Thursday's outfit with this moment's weather is wrong exactly when it matters.
- `src/lib/planning/plan-rules.ts` — the rules a plan must satisfy, **verified in code rather than trusted to the prompt**. Both were stated in the prompt and Haiku broke both on its first two real runs, which is D8 being violated by its own author: these are exactly decidable, so they belong in TypeScript.
  - **Composition** (`MAX_PER_CATEGORY_IN_SEGMENT`) — how many of a category can physically be worn at once in one segment: one bottom, one dress, one pair of shoes, one bag; two tops and two outerwear because layering is real; four accessories. The generator produced a segment with two pairs of trousers. Bags and accessories were initially uncapped, which left no upper bound on outfit size at all — a wardrobe with ten belts could be told to wear six; capping every category bounds a segment at 11 items worst case, with realistic outfits at 5–7. Enforced **deterministically** by `enforceComposition()` as the last step before persisting, in both the weekly and daily routes — "keep one pair of trousers, not two" needs no judgement, and an impossible outfit must not be able to reach the database even if a repair call misbehaves.
  - **Incompatibility** (`INCOMPATIBLE_WITH`) — a dress is never combined with a top or trousers; it already covers torso and legs. Per-category caps alone allowed it, since each piece was under its own limit. Outerwear is deliberately *not* incompatible (a blazer over a dress is a real outfit), so a cardigan classified as `Tops` will now be kept away from dresses — if that pairing matters, the item belongs in `Outerwear`. When trimming, the dress wins: dropping it instead would leave a look that also fails coverage.
  - **Coverage** (`REQUIRED_SLOTS`) — what a segment must contain to be an outfit at all: something on the torso, something on the legs, something on the feet, where a dress satisfies the first two. The generator once produced a day whose entire outfit was one pair of sandals, because until then the rules only said what was *too many*, never what was too few. `enforceCoverage()` fills a missing slot from the candidate pool, choosing an item that isn't already in the segment and isn't worn too close by, so filling a hole can't create a rotation violation.
  - **Weather** (`TOO_WARM_FOR_SLEEVES_C = 30`, `isLongSleeve()`) — above 30°C a day gets no outerwear and no long-sleeve tops or dresses. Season tags don't catch this (items are routinely tagged spring *and* summer) and the candidate filter works on the whole week's range, so a week containing one 32°C day still has to keep sweaters available for the cold days — it has to be per-day. There is no sleeve column, so it's inferred from category (all outerwear counts) plus conservative subcategory/material keywords; a false positive would remove something the user owns for no reason. Weekly uses the forecast's daily maximum; daily only has one representative temperature, so it's marginally less strict there.
  - **Rotation** (`MAX_WEAR_DAYS_BY_CATEGORY`, `ROTATION_WINDOW_DAYS = 7`) — **how many days out of any seven** an item may be worn on, per category, measured over a rolling window. Defaults: tops, bottoms, dresses and outerwear 1 day; shoes 2; bags and accessories 3. Repeats *within* a day are never counted — one blazer carrying through several segments is the point.
    - This replaced a "minimum gap in days between wearings" table, and the difference is the whole bug it was changed to fix: a 2-day gap silently permits three wearings a week (Mon/Wed/Fri), which is how the same sandals kept coming back, and bags/accessories were exempt entirely, which is how one clutch became the only bag in the closet. Counting days is also how the rule is naturally said out loud, so the setting and the guarantee are now the same sentence.
    - **The limits are the user's**, stored in `profiles.rotation_limits` (schema section 19) as only the categories they changed, merged over the defaults by `resolveRotationLimits()`. Nothing reads the constant directly — every rule function takes a `RotationContext`, and `describeRotationLimits()` builds the prompt text from the same resolved map, so the model is never aimed at a number the enforcement doesn't use. Read via `readRotationLimits()` in `plans.ts` as its **own** query rather than a column on the planners' profile select: this repo applies schema by hand, and a missing column on that select would 400 the whole query and take planning down with it. Edited from `/plan`'s **Repeat rules** button (`plan/rotation-settings.tsx`), not `/profile` — the question is asked while looking at the week, and it's the only `profiles` column edited elsewhere for that reason.
    - **The window doesn't restart with the request.** `RotationContext.history` carries the dates each item is already committed to on the surrounding days, read from the stored plans (`readWearHistory()`). Without it, "once a week" restarted every Monday and one day redone on its own re-used whatever the other six already had — which is most of why the same few pieces kept reappearing. Weekly loads the six days before the window plus any in-window day already `worn`; daily loads ±6 days around the date, excluding it.
    - **Daily enforces rotation too, and didn't used to.** The reasoning was that one day can't repeat against itself; it can't, but it can repeat against the week around it, and skipping the check made "Redo this day" the fastest way to break the week it belongs to.
    - **An unswappable repeat is now taken off rather than kept**, when the category covers no required slot (`isDroppableCategory()` — outerwear, bags, accessories). Keeping it was the reason the setting looked broken: a user who owns one blazer and sets Outerwear to one day a week has no substitute *by construction*, so "swap if you can, otherwise keep and warn" meant the same blazer on three days of the week with the limit sitting in the UI saying otherwise. Shoes, tops, bottoms and dresses still stay when nothing is free — barefoot is worse than a repeat — and those remain warnings. The cost is real and intended: on a small closet the later days of a week lose their outerwear and bag rather than repeating them.
  - **Comfort** (`enforceComfort()`) — what a segment can't contain given what it *is* and what the day did *before* it. Four reasons, checked together in `comfortReasonFor()` so that fixing one can't cause another (swapping heels off a flight must not reach for the trainers that were just run in, and neither may reach for gym kit to wear to a board meeting):
    - `"transit"` — heels on a flight. A Monday holding a 10am team meeting, a 5pm departure for JFK and an 8:30pm flight to London came back as the same tailored trousers, blouse and **white pumps** all day, swapping only the bag for the overnight flight: the classifier had rated every event of a business trip at the trip's formality, so the arithmetic in `occasion-groups.ts` saw one continuous block. `isHardToTravelIn()` is deliberately footwear-only and conservative (`heel`, `stiletto`, `pump`, `slingback`, `court shoe`, `wedge`, and only within `Shoes`): "is this a heel" is decidable from the columns we store, "is this blazer too stiff for seven hours of sitting" is judgement and stays with the model, which the prompt asks for.
    - `"too_casual"` — sport kit at a formal occasion, the mirror image of `"sweat"`. A segment whose formality is ≥ `MIN_FORMALITY_BANNING_ACTIVEWEAR` (3, where the calendar's scale turns into work) takes no activewear. `isActivewear()` needs two agreeing signals and is deliberately hard to trip: an item the classifier tagged `work`, `formal`, `party` or `wedding` is never activewear whatever it's called, and otherwise it's either tagged *only* `sport` or matches an unambiguous keyword (`leggings`, `joggers`, `track pant`, `sweatpants`, `running`, `gym`…). Plain sneakers tagged `casual` don't match — the point is gym kit in a boardroom, not a war on flat shoes. Segments that **are** sport can't trip this at all: `MAX_FORMALITY_BY_KIND` already caps them at 2, which is why `SegmentContext.formality` must come through `formalityForKind()` rather than raw from the event.
    - `"sweat"` — anything worn in an **athletic** segment earlier the same day is unavailable for every later segment of that day. This is what makes sport more than a low formality: you change afterwards. Bags and accessories are exempt, on the same reasoning that gives them the loosest rotation limit — the same tote before and after tennis is normal, and flagging it would be noise.
    - `"not_sport"` — the positive half of the sport rule, and the last one added: an **athletic** segment may only contain clothes and shoes you could actually play in. `"too_casual"` said what sport kit may not do; nothing said what a sport segment must be, so golf kept arriving in a casual midi dress, black dress trousers and white pumps. `isSportSuitable()` is deliberately the mirror image of `isActivewear()`: the classifier's own `sport` occasion tag is sufficient **on its own**, because this rule decides what may *stay* rather than what must go, and the user's instruction was literally "a sport occasion wears the things tagged for sport". A broader keyword list (`polo`, `golf`, `tennis`, `trainer`, `sneaker`, `performance`, `jersey`…) catches club kit that reads as smart. Only what is worn against the skin has to qualify — a tote, a straw hat and sunglasses are fine on a course.
    - The swap is 1:1 where the category covers a required slot, and a plain removal where it covers none (`isDroppableCategory()`, same helper as rotation) — a blazer on a golf course has no business being kept just because the closet holds no second one. **A second pass then handles what a 1:1 swap structurally cannot**: a gray wool midi dress at a golf round has no replacement *as a dress* in most closets, so the first pass kept it and the segment stayed wrong. It is now dropped and torso+legs refilled from the pool (`fillMissingSlots()`, shared with `enforceCoverage`), with the whole change reverted unless the result is still a complete outfit. Where it isn't — the only pair of shoes, a closet with no sport clothes at all, a second athletic session with one set of kit the sweat rule forbids reusing — the item stays and the caller reports it, because barefoot is worse than badly dressed. Segments are walked in order so each sees the already-corrected versions of the ones before it.
    - A rule the candidate filter can starve is not a rule, so `selectCandidates` takes `pinnedIds`: when any day of the window holds an athletic occasion, weekly pins every sport-suitable item into the candidate set. Without it a golf round the calendar rated formality 4 (client, private club, working day) mapped to work/formal/party occasions, which filtered every `sport`-tagged piece out — and left this rule with nothing to swap the pumps for.
  - Violations trigger **one** targeted repair call rebuilding only the offending days, naming the specific item and date rather than restating the rule (restating it is what already failed). Then every rule is enforced deterministically anyway — `enforceComposition` → `enforceWeather` → `enforceCoverage` → `enforceComfort` → `enforceRotation`, in that order because removing something can open a hole, filling a hole can put heels back on a flight, and any swap can create a repeat. Three rounds of "the prompt says so and it did it anyway" is why these are guaranteed rather than requested; a code-chosen substitute styles worse than the model would, but it beats shipping a look that can't be worn. Anything still unsatisfiable — a genuinely too-small wardrobe — comes back as `warnings` and is shown in the UI rather than swallowed: a repeat the user can see explained reads as a closet limitation, an unexplained one reads as carelessness.
  - The daily route runs composition, coverage and comfort too, and the same merge and text-alignment passes. `/home` can produce the same broken looks; it just hadn't yet. The single-segment redo path shares them at segment granularity: it scrubs the new segment's reasoning against whatever the rules removed, and rebuilds both its `changeFromPrevious` and the following segment's `nextChangeFromPrevious` from the real diff when the items moved.
- `src/lib/planning/occasion-groups.ts` — **how many segments a day needs is computed, not asked**. `groupOccasions()` groups consecutive calendar occasions whose formality differs by less than `FORMALITY_BREAK` (1), and both prompts are given the resulting groups as the required segmentation with their exact event ids. Leaving the merge decision to the model was unstable: the same day — 9:45am board meeting (formality 4), 3pm client call (3), 8:15pm dinner (3) — came back as two segments on one run and one on the next. An occasion with unknown formality joins the open group rather than forcing a split, so missing data can't manufacture an extra outfit change.
  - **A change of `kind` splits a group regardless of formality**, and it is the only thing besides formality that does. `occasionKind()` returns `transit`, `athletic` or `general`; a group's kind is carried into `describeGroups()` for the prompts and its formality is capped by `MAX_FORMALITY_BY_KIND` (2 for both non-general kinds), so a flight rated 4 because it belongs to a business trip — or golf rated 4 because it's at a client's club — cannot pull the segment up to boardroom tailoring. Whether you are on a plane or on a court is not a matter of degree, so it can't be left to the formality distance: that is exactly how a day of meetings and an overnight flight came back as one outfit in heels, and how a client golf round merges into the surrounding suits. Both prompts explain the kinds and say this is where a complete change of outfit is expected rather than avoided.
  - **Two `athletic` occasions don't share a segment either**, unlike two `transit` ones. You don't change between the taxi and the plane; you do change between a round of golf and a tennis match. The cost is a calendar that splits one session into adjacent entries ("warmup", then "match") getting two outfits — and the sweat rule in `plan-rules.ts` would have forced their outfits apart anyway.
  - `occasionKind()` reads the classifier's `occasion` label and the user's own event title **against separate pattern lists**, because they fail in opposite directions. `occasion` is a deliberate one-word answer, so a bare `travel`, `train` or `run` there means what it says; a title is prose, where "Travel budget review", "Train the new hire" and "Run through the deck with Priya" are meetings, so titles only match phrasings that can't be anything else (`flight`, `depart`, `train to/from`, `morning run`, `personal training`…). Checking the title at all is what makes the rules work on **already-classified** rows: sync only classifies events where `occasion IS NULL`, so "Depart for JFK" and "Golf with the Hendersons" are caught by their titles without anyone re-running a sync. All-day events are never `transit` — "Business Trip (London)" spans every hour of the day including the meetings, and matching it would dress a whole workday for a plane — but all-day `athletic` is kept, since an all-day "Golf Tournament" really is a day of sport rather than a container around one.
  - `classifyEvents()`'s prompt also now says an event that *is* the journey, or *is* sport, gets formality 1–2 however formal its company or venue is, while an all-day trip container is judged by its purpose. That only affects newly classified rows; the deterministic rules above are what fix existing ones.
- `src/lib/planning/merge-segments.ts` — after composition/weather/coverage/comfort/rotation enforcement, daily and weekly generation deterministically merge adjacent segments that wear the same look. `groupOccasions` decides how many segments a day *may* have, from the calendar; this decides how many it actually earns, from the clothes.
  - **The test is on the CORE, not on the whole item set.** Set equality only caught lists the model returned identically, and what it actually returned, run after run, was a board meeting and the client lunch after it in the same blazer, trousers, shirt, bag and belt with the ankle boots changed for wedges — three "different" outfits a day that were one outfit and a shoe rack. So if `Tops`/`Bottoms`/`Dresses`/`Outerwear` are identical, swapping the shoes or the bag is not a change of outfit and does not earn its own segment. A real change — office tailoring becoming a cocktail dress, work clothes becoming sport kit — moves a core piece, so it never merges.
  - The survivor keeps the **first** segment's items: a day generally runs from its most formal occasion downward, and where it doesn't the clothes themselves differ and nothing merges. Its reasoning is kept whole rather than concatenated with the second's, which exists to explain a change that no longer happens. Segments of different `kind` never merge, and an `athletic` segment never merges with anything — it is a separate look by definition, so collapsing one would hide a rule failure rather than tidy a duplicate. Non-adjacent repeats stay separate because an intervening outfit change is real.
- `src/lib/planning/segment-text.ts` — **`alignSegmentText()` makes the words match the canvas.** Every rule in `plan-rules.ts` runs *after* the model has written its reasoning, so the model routinely explained a look it no longer described: a golf segment reading "Retained the brown wedge sandals" while the canvas showed the pumps the comfort rule swapped in, and a first segment carrying a `changeFromPrevious` inherited from the repair call, describing a change from the previous *version of the plan* rather than from the previous segment of the day. Neither is fixable in the prompt — the text is written before the change exists — and a second model call would pay a generation to restate facts we hold exactly.
  - Each segment is stamped with `originalItemIds` before enforcement and carries it through (every `enforce*` spreads the segment), so this pass knows which pieces the rules replaced underneath the prose. Any **sentence** naming a piece that is no longer present is dropped, matched on two agreeing significant words rather than a substring, since the model rarely quotes a label verbatim. `changeFromPrevious` is rebuilt from the real item diff whenever either side moved or the previous segment absorbed a merge, and deleted outright on the first segment of a day; the model's own wording survives only when nothing changed, because it says *why* and a diff can't. Runs **after** merging, since consolidation changes which look a segment transitions from. `scrubReasoning()`/`describeTransition()` are exported for the single-segment redo, which rewrites one segment between two it may not touch.
- Model is Haiku with `max_tokens: 8000`. ROADMAP calls weekly the one planning call that might justify Sonnet; try Haiku's output quality first and check `checklist.md`'s cost table before switching.
- **The window is not always seven days.** `?days=` (clamped to `MAX_PLAN_WINDOW_DAYS = 14`, exported from `plans.ts`) and `?keep=<comma-separated dates>` exist for travel mode, which plans a trip of whatever length through this same route. The cap is a token budget, not a forecast limit: one generation is `max_tokens: 8000` and each day costs one to three segments of JSON, so a longer request would be a truncated plan rather than a longer one. `keep` names dates this call must not overwrite; they are still sent to the model (marked `alreadyWorn` in the outline) and still merged into the rotation history, so the days that *are* written are chosen around them, and `replace_weekly_plans` skips them at persist time and returns them in `skippedDates` next to the worn ones.

### Travel mode (`/travel`)

ROADMAP 6.3. `/travel` finds trips on the calendar, plans each one, and turns the days the user confirms into a packing list.

**Trips are detected, not typed in.** `src/lib/travel/detect-trips.ts` takes 30 days of `calendar_events` and returns the trips in them, in TypeScript with no model call — the same D8 reasoning as `occasion-groups.ts`: it is decidable from an event's coordinates, its local date span and its title, and a model asked twice would return two different trip counts, which would re-key every stored trip and orphan its packing list.
- An event is **away** when its coordinates are more than `AWAY_RADIUS_KM` (120km) from `profiles.lat/lng`, or when its title states a destination outright (`explicitTravelDestinationFromTitle`, shared with Calendar sync). 120km is generous on purpose: a card reading "Trip to New York" for someone who lives there is worse than missing a real trip. With no home coordinates saved, only the stated form counts — without something to compare against, every located event would read as a trip.
- Away dates are merged into runs, bridging gaps of up to `MAX_GAP_DAYS`, so a Tuesday with an empty calendar between two London days is still London. A run is then extended by one day on each side if that day holds a `transit` event, which is what a 5pm "Depart for JFK" geocoded to the *home* airport is.
- A run needs 2+ days to be a trip unless the calendar says so in words — one meeting in another city and back is an errand.
- **Business vs leisure** is title-first (`Business Trip`, `Conference`, `Offsite` / `Vacation`, `Wedding`, `Getaway`), falling back to counting the trip's own non-transit events by formality and occasion. Transit is excluded from that count because every trip has flights and counting them would only measure length. The reason is carried as `typeReason` and shown in the badge's tooltip, so the classification is never a black box — and the user can override it, after which the stored value wins.

**A trip's outfits are ordinary plans.** This deliberately departs from ROADMAP 6.3 step 5, which predates 6.2's "a date has exactly one plan": writing `source='travel'` rows with a `travel_plan_id` would give a trip Thursday and a `/plan` Thursday, two independent generations of the same date with nothing syncing them — the exact bug 6.2 removed. So `/travel` reads and writes the same `outfit_plans` rows `/plan` does, through the same `GET/POST /api/ai/weekly` with `?start=&days=`. "If it's already planned, pull it in" is therefore not a copy; it is the same row. `travel_plans.daily_outfits` and `.weather_data` stay unused, and `outfit_plans.source='travel'` remains unreached by any code path.

**`travel_plans` holds only what detection can't derive** (schema section 21): `calendar_signature`, `trip_type`, `confirmed_dates`, `packing_list`, `share_token`.
- `calendar_signature` is the trip's **first local date plus its normalized destination** — deliberately not the end date and not the event ids, because a trip routinely gains a meeting or loses a day between two visits and re-keying on any of that would fork the row and strand the packing list on the old one. The constraint backing it is a real `unique (user_id, calendar_signature)` rather than a partial index: resolving a trip is an upsert, and Postgres can't infer a partial index from an `ON CONFLICT` target that doesn't repeat its predicate, which PostgREST never emits. Plain `UNIQUE` (NULLs distinct, unlike `outfit_plans_cache_key`) is what lets any number of signature-less manual rows coexist.
- Rows are created **on first open**, not on detection: `POST /api/travel/trips/resolve` takes a signature, re-derives it from the calendar (so a caller can't invent a trip they don't have), and upserts. A calendar full of trips nobody opens stays out of the table.
- Where the row and the calendar disagree, **the calendar wins for dates and cities and the row wins for decisions** — `readTripMeta` re-detects on every read for exactly that reason. A stored trip that no longer detects still resolves, from its own dates, rather than 404ing and taking the packing list with it.

**Confirmation is the whole difference from `/plan`.** Per-day "Confirm & pack" writes `confirmed_dates`, and the packing list's garment half is *derived* from those days — `garmentsForDays()` is the union of the items in the confirmed segments, so the list structurally cannot disagree with the outfits. It is not editable there: the only honest way to change what you're packing is to change an outfit. A checkbox next to a garment means "this is in the bag", never "this is on the list". Redoing a confirmed day clears its confirmation, since the clothes the packing list was built from are no longer in the plan.

The non-garment half is a **fixed template plus the user's own additions, never generated (D11)** — a model forgets the phone charger and invents an adaptor the user doesn't own, and neither shows up until they're at the airport. `resolvePackingList()` merges the stored column over the current template by id, so relabelling an entry in code reaches every existing trip; a template entry the user removed is recorded in `hiddenTemplateIds` rather than by absence, which is the difference between "I don't need this" and "this trip predates that entry".

**Planning a trip keeps what's already there.** "Plan the other N" passes the already-planned dates as `keep`; a full "Replan the trip" passes the confirmed ones. Both go through the weekly route, so a trip's outfits are subject to the same rotation, composition, coverage, weather and comfort rules as everything else — the user chose that over a minimal-capsule objective, so nothing here relaxes the rotation limits.

**Two ways out of the app**, both from `TripPrintout` so the layouts can't drift:
- `/(print)/travel/[id]/print?section=all|cards|packing` — D7: `@media print` and the browser's own "Save as PDF", not puppeteer (Vercel serverless would need `@sparticuz/chromium` bundled, and the cold start and bundle size cost more than the feature). Its own route group so the dashboard chrome is *absent* rather than hidden. Cards are a **deterministic category-ordered grid, not the freeform Canvas (D6)** — generated segments carry no `x/y/width` at all, and a printed card answers "which pieces am I taking". Images are eager plain `<img>`; a lazy or blurred one prints as an empty box and the failure only shows up on paper. Weather comes from the plan's stored snapshot rather than a fresh forecast, so the card says what the outfit was actually chosen for. `?section=` exists because the list is used before leaving and the cards after arriving.
- `/trip/[token]` — a public, unauthenticated read-only page, so a trip can be forwarded to someone without an account. The token is 128 bits of CSPRNG minted by `PATCH /api/travel/trips/[id]`, the row is looked up *by* it, and revoking clears it, 404ing every copy of the link at once. Backed by the service role because every table involved is scoped to `auth.uid()` and there's no session here to match — which is why that page reads one fixed shape through `readTripRenderData` and never accepts a caller-supplied id, table or column. `robots: noindex`, and `/trip` is deliberately absent from `proxy.ts`'s `isDashboard` list.

`src/lib/travel/trip-render.ts` is the one server-side reader both of those pages use (neither can call `/api/ai/weekly`), and the only place that flattens the two shapes stored under `outfit_plans.weather` — weekly writes `DailyForecast` entries, daily writes `WeatherData` ones, both under `{ locations: [...] }`.

### The human stylist console (`/pro`) and her suggestions

ROADMAP Phase 10-A, decisions D15/D16/D17. A human stylist reviews a client's closet and saved Looks, rates them, writes a note, and optionally re-arranges the outfit on the shared Canvas. Everything she saves is a **proposal** — it does not touch the client's rows until the client accepts.

- **A staff-only account (`roles = {stylist}`) gets a different app.** The sidebar drops to Clients alone — Profile too, since that page is entirely client-side settings (city, timezone, Calendar connection, sharing switches) and Sign out lives in the sidebar rather than inside it, so nothing is stranded by removing it — and `/home` redirects to `/pro` — sign-in lands on `/home` because `proxy.ts` sends it there, and the proxy can't check roles without a per-request DB query. An account carrying **both** roles keeps the whole client app plus Clients; that's the owner/dev case, and hiding the client side from it would make the product untestable.
- **Route is `/pro`, not `/stylist`** — `/stylist` is the client-facing AI stylist page. `/pro` lists clients with an open access window; `/pro/[clientId]` is the workspace.
- **The workspace is five tabs**: *Overview*, *The week ahead* (the days they've planned, reviewed one planned look at a time), *Saved Looks*, *Every piece* (the closet itself, one garment at a time), and *Build a look*. Tabs rather than stacked sections because a full closet sitting under the others is a scroll, not a workspace. Overview leads because it's the only tab that answers "who am I looking at" — every other tab assumes you already know — and it's the only read-only one. Three of the four working tabs open the shared Canvas and carry a proposal; *Every piece* cannot — see the item-review bullet below.
- **Overview** (`src/lib/stylist/client-overview.ts`) is profile + service status + sessions, all service-role and gated by the same access window. Two different reasons for the service role: the `profiles` columns *are* reachable under her own session via 18b, but the page already reads that row for the window, so a second query would be waste; `stylist_bookings` is **not** in the 18b whitelist and never will be (availability has to consider other users' occupied intervals without exposing them), so her sessions with *this* client are projected here — narrowed to service type, start, end, status. "Past communication" is deliberately only what the product actually records — booked consultations and suggestions already sent. There is no message store or CRM sync yet (ROADMAP: Folk), and a section that is always empty reads as a bug rather than as an unbuilt feature.
- **A new Look she builds from scratch is still a proposal (`target_kind = 'new_outfit'`).** It's the one kind with no target row at all — the Look doesn't exist until the client accepts, and **accepting is what creates it**: `accept_stylist_review()` inserts the `outfits` row (`ai_generated = false`; a human built it) plus its `outfit_items`, and records the new id in `stylist_reviews.created_outfit_id` so undo removes exactly that Look and nothing else. Undo therefore deletes rather than restoring a snapshot, which is why `revert_stylist_review()` branches on this kind before the "there is no earlier version to restore" guard — `previous_items` is legitimately empty here. The FK is `on delete set null`, not cascade: if the client later deletes the Look themselves, the record that she once proposed it should survive. The schema's target check requires `has_proposal = true` and a non-empty `proposed_name` for this kind, because a Look arriving in someone's closet as "Untitled" would be worse than one they saved themselves. Letting `/pro` write an `outfits` row directly was the obvious alternative and would have broken the one rule the whole console runs on. Both are protected by `src/proxy.ts` (signed-in) *and* by the role/window gate below, checked in the pages themselves.
- **Access gate (D16)**: viewer's `profiles.roles` contains `'stylist'` **and** the client's `profiles.access_expires_at` is in the future. There is deliberately no `wardrobe_grants` table — with one stylist every row's `stylist_id` would be the same value. The window is written by `/api/webhooks/consult-ended` (automation, 14 days, D14) and the client can end it early from `/profile`. **The rule exists twice**: `public.stylist_can_view()` (schema 18a) is what actually protects the data; `src/lib/stylist/access.ts` mirrors it for routing and copy. Change one, change the other. `stylist_can_view()` must stay `security definer` — it is attached to a policy on `profiles` and reads `profiles`, so an invoker function would recurse.
- **RLS is a whitelist**: `stylist_can_view()` is attached as one extra SELECT policy on exactly `wardrobe_items`, `outfits`, `outfit_items`, `wardrobe_item_photos`, `profiles`. `calendar_events`, `google_connections`, `outfit_journal` and the `outfit_plans` family have none, and neither will any table added later. Forgetting to add one is safe; adding one by reflex is not.
- **`wardrobe_access_log`** records every server-side read. Client-readable, stylist-invisible. Built now because a log added later has no history.
- **Occasion sharing is three levels (D17)**, all in `src/lib/stylist/occasion-projection.ts`, all server-side against the service role:
  - **L0** (default) — closet and Looks only.
  - **L1** (`profiles.stylist_share_occasions`) — per day: generalized wording and formality. **The planned outfits themselves are not gated by this** — a planned look is wardrobe data, not calendar data, and it is the main thing the stylist is there to review; only the *description of what it's for* is calendar-derived. Gating both was the original implementation and it left the console unable to show the very thing the feature exists for. With L1 off the calendar is not queried at all, and a segment is labeled "Look N" instead of by its occasions. The wording is assembled from two enums, `calendar_events.occasion` + the new `calendar_events.companion`, through fixed lookup tables. It never passes through the event title, so it *structurally* cannot leak a name — unlike asking a model to redact, which works until it doesn't. `occasion` is model-authored free text, so unrecognized values fall back to formality-based wording rather than being echoed.
  - **L2** (`calendar_events.stylist_share_detail`, per event) — that one event's time and raw title. Toggled from `/plan` next to the occasion itself, and hidden entirely when L1 is off, since L2 alone reveals nothing.
  - **`outfit_plan_segments.label` / `.reasoning` are never projected.** Haiku wrote them from the title and will say "for your meeting with Sarah". The stylist sees a segment name re-derived from its events' enums.
- **`classifyEvents()` now also returns `companion`** (a closed enum — free text there would be rendered to the stylist verbatim) in the same batched call, at no extra cost. `/api/google/calendar/sync` selects rows where `occasion IS NULL OR companion IS NULL`, so existing rows backfill on the next sync instead of reading "with someone" forever.
- **A review of one wardrobe piece (`target_kind = 'item'`) never carries a proposal.** A lone garment has no arrangement to change, so `'item'` is a rating and a comment on `stylist_reviews.target_item_id` and nothing else. That is enforced by the schema's target check (`has_proposal = false` is part of the `'item'` branch), not by the route alone — the route rejects it too, so a caller that sends items learns its request was wrong instead of having them silently dropped. `stylist_target_items()` returns `[]` for this kind, which makes `accept_stylist_review()` a pure acknowledgement: nothing to snapshot, nothing for undo to restore. The client's inbox reuses the existing no-proposal card ("Got it" / "No thanks") and additionally renders the piece being discussed, since a note about an item shown without the item reads as being about nothing.
- **The proposal tables**: `stylist_reviews` (target is an `outfits` row, an `outfit_plan_segments` row, a `wardrobe_items` row, or nothing at all for `new_outfit`; rating, note, and `has_proposal` are each independently optional but not all three) + `stylist_review_items` (same shape as `outfit_items`, so her arrangement transfers verbatim). Both carry **read policies only** — the stylist writes through `POST /api/stylist/reviews` (service role, validates the target and every item against the *client's* wardrobe in one place), and the client answers through `POST /api/stylist/reviews/[id]/respond` → the `accept_stylist_review` / `decline_stylist_review` / `revert_stylist_review` RPCs.
- **Accept overwrites the target and snapshots what it replaced.** A re-arrangement requires the stylist to write an updated outfit description. Accept applies that copy to `outfits.notes` or `outfit_plan_segments.reasoning`; for plan segments it also clears the target and following segment's now-stale `change_from_previous` text. `stylist_reviews.previous_items` preserves ids + geometry and `previous_text` preserves the old description and both affected transitions, so undo restores the complete prior version. Undo lands in `'reverted'`, not back in `'pending'`, so it doesn't reappear as unanswered. All three target FKs are `on delete cascade`: a Look the client deletes, a segment a regeneration replaces, or a piece they remove from the closet takes its pending suggestions with it rather than leaving an accept button pointing at nothing.
- **Accepting deliberately bypasses `src/lib/planning/plan-rules.ts`** (composition, weather, rotation). Those rules exist to stop a model producing an unwearable look; a human stylist outranks them.
- **Nothing in `/pro` calls a model.** She is the human alternative to `/stylist`; a model call here would have no product reason and a real cost.
- **Accepting reloads the page, deliberately.** The surfaces that render a plan — `DailyRecommendation` on `/home`, `WeekView` on `/plan` — are Client Components holding their own fetched state, so `router.refresh()` (Server Components only) left them showing the pre-accept outfit until the user happened to reload. `review-inbox.tsx` calls `window.location.reload()` after accept and undo for that reason; decline stays on `router.refresh()` because nothing outside the card changed.
- **A suggestion changes exactly its target.** Accepting a review of a saved Look rewrites that Look's `outfit_items` and shows up in `/outfits` — it does **not** touch `/home` or `/plan`, which render `outfit_plan_segments`. Those are different objects by design (D5: generated plans never become `outfits` rows). To change what the client wears on a given day the stylist must review that day's planned look from the console's week panel, which targets the segment.
- Client-side surface: `src/lib/stylist/reviews.ts` (reads under the client's own session — this is ordinary owned data) feeds `src/components/stylist/review-inbox.tsx`, mounted above the daily plan on `/home`. A pending card compares the target's current arrangement with the proposal. After accept, the target itself is already the proposal, so the card must use the accept-time `previous_items` snapshot for its **Before** side; reading the target again would render the stylist's version twice.
  - **The inbox is collapsed by default and each suggestion is one strip.** It sits *above* the daily plan, so an expanded stack of full-width Before/Her-version comparisons pushed the thing the client came for off the screen. The two collages ride at the strip's right end as 56px thumbnails (`Before → Her version`); clicking them — or the chevron — expands that one strip to the full-size comparison and the untruncated note. Accept / No thanks / Undo stay visible on the collapsed strip, so answering never requires expanding.
  - **Only `pending` rows sit under the heading; answered ones move behind a "Reviewed" button beside it**, which is also where an accepted suggestion's undo now lives. `readStylistReviewsForClient()` therefore reads **every** status and filters nothing — the split is the component's, and a row dropped in the query could not appear in the history. (It used to select only `pending`/`accepted` and additionally drop answered no-proposal rows, on the reasoning that an answered rating had nothing left to act on; that is still true of its *buttons*, but it is a record, so it belongs in the history.) A row with no proposal to restore gets no undo button there.

### The shared outfit Canvas

`src/components/outfit/outfit-canvas.tsx` owns the freeform collage interaction — drag to move, corner to resize, bring-to-front on manipulation, bounds and 15%–60% width clamping — plus the closet picker beside it. It lived inside `outfits-view.tsx` until `/home` needed the same editor for "Adjust this segment"; two copies of pointer-gesture code would drift.

Everything is generic over `CanvasItem`, the minimal shape (`id`, `category`, `subcategory?`, `color?`, optional `optimized_url`, `clean_url`, `original_url`) that both `WardrobeItem` and `DailyWardrobeItem` already satisfy, so neither caller converts its data first. `layoutsFromRows()` builds a layout map from rows whose `x/y/width` may be null, filling gaps from `defaultLayoutFor(index)` — null geometry means either a pre-layout record or an AI-generated look, since the model never produces layout. `OutfitCollage` is the read-only render used by `/home` to display a segment with the arrangement the user actually made.

### The upload pipeline (core flow)

`POST /api/ai/classify` (`src/app/api/ai/classify/route.ts`) is the central pipeline:
1. Client already uploaded the original image to Supabase Storage (`wardrobe` bucket) and passes `{ originalUrl, storagePath, mode }`. `mode` is `"single" | "multi"`, set by a toggle in `UploadZone` (`src/components/closet/upload-zone.tsx`) that the user picks *before* uploading — defaults to `"single"`.
   - `mode: "single"` **skips the detection vision call entirely** — the route sets `itemCount = 1` and goes straight to the single-item branch. This is the common case, so it's the one worth not paying detection tokens for.
   - `mode: "multi"` still calls `detectItems()` (still needed for concrete SAM prompts) but trusts the user's claim over Claude's count guess: `itemCount = Math.max(2, detection.count)`.
   - `mode` omitted (older client) falls back to the original auto-detect behavior below, for backward compatibility.
2. `detectItems()` (`src/lib/ai/segment.ts`) — only called when `mode` isn't `"single"` — makes a Claude Haiku vision call asking for both the distinct-item count and concrete English object nouns for SAM 3.1. Before the `mode` toggle existed, this ran unconditionally on every upload; see `checklist.md` for why running SAM first instead would cost money on every single-item photo just to find out it's one item.
3. **Single item (count ≤ 1)** — unchanged original pipeline: `removeBackground()` (`src/lib/ai/remove-bg.ts`, fal.ai `fal-ai/birefnet/v2`) → re-upload clean PNG to Storage (`_clean.png` suffix) → `classifyItem()` → insert one `wardrobe_items` row. Response: `{ item, classification, multiItem: false }`.
4. **Multi item (count ≥ 2)** — `segmentItems()` (`src/lib/ai/segment.ts`) calls fal.ai `fal-ai/sam-3-1/image` once per distinct concrete noun, requests multiple masks plus scores/boxes, deduplicates overlapping detections, and crops the original pixels locally from normalized `[cx,cy,w,h]` boxes. It deliberately does not crop the SAM applied-mask PNGs because those use a black background. Before returning, `mergeDuplicateAccessories()` groups every detection by its normalized prompt (`shoe`, `earring`, `bracelet`, or whatever noun Claude used) and, for any group with 2+ crops, calls `classifySimilarItems()` to ask **Claude Sonnet** (not Haiku — see below) whether any of them depict the same physical item photographed twice — it must describe shape/material/color/hardware/brand per crop before deciding pairs vs. singles (returned as `FINAL:{"pairs":[[1,2]],"singles":[3,4]}`); a proximity/color-only heuristic was tried first and wrongly merged unrelated items that happened to sit near each other, so grouping is deliberately vision-verified, not geometric. Confirmed pairs are composited side-by-side via `composeSideBySide()`, ordered by each item's actual `detection.box[0]` (normalized center-x) in the source photo so the one physically on the left ends up on the left of the composite — asking Claude to additionally judge shoe chirality (which one is the left/right foot) was tried and abandoned because it was unreliable (it once called both shoes of an identical pair "right foot" and refused to merge them); geometric photo position is deterministic and doesn't have that failure mode. `shoe` and `earring` are in `MIRROR_IF_LONE_PROMPTS` — categories that are always sold/worn as a matched pair — so an unmatched lone item there is additionally mirrored with `sharp().flop()` (a literal pixel-flip, so it can't fabricate a different design) and composited next to its mirror. Any other category (bracelet, etc.) is left as a genuine single with no mirroring — a lone bracelet is already a complete item — and a group with only 1 detection skips the Sonnet call entirely (no cost for the common non-duplicate case). Any item Claude doesn't confidently group defaults to single — an incorrect merge is worse than two single-item entries. Each resulting crop is uploaded to Storage, then run through the *same* remove-bg → classify → insert steps as the single-item path (shared via `processOneItem()` in the route file) — one `wardrobe_items` row per detected item/pair. A failed segment is skipped, not fatal. Response: `{ items: [...], multiItem: true, count }`.
   - **Verified 2026-07-10**: a live `fal-ai/sam-3-1/image` call on the four-purse test image returned four entries in `masks`, `scores`, `boxes`, and `metadata`. The endpoint requires a concrete text prompt and explicit `return_multiple_masks`; broad prompts can return no masks.
   - **Verified 2026-07-10 (shoe pairing)**: a 3-real-pairs photo correctly yields 3 shoe entries, and a 6-unrelated-single-shoes + 2-bag photo correctly yields 6 mirrored singles + 2 bags with no cross-pairing. `classifySimilarItems` deliberately uses **Sonnet, not Haiku** — Haiku's per-shoe descriptions were unstable across camera angles (a crossed-over pair with one shoe sole-up and the other side-on got described as if they were different designs) and it kept missing genuine pairs; this call only fires when 2+ crops of the same category are detected, so the cost of a stronger model here is rare, not per-item like `classifyItem`/stylist. Two gotchas from that switch: Sonnet 5 emits an extended-thinking block before its text block, so `message.content[0]` is not the text — find it with `content.find(b => b.type === "text")`; and Sonnet's verbose per-item reasoning needs `max_tokens: 4096` or the response gets cut off before the `FINAL:{...}` JSON, silently falling back to "all singles". See `checklist.md` Debug Log ("鞋子配对") for the full history.
   - **Not yet live-verified**: the bracelet/earring generalization (only the shoe case has been tested against a real photo so far).
5. `classifyItem()` (`src/lib/ai/classify.ts`) downsizes with Sharp (max 1024px, JPEG q85 — Claude rejects images >10MB, and smaller images cost fewer tokens); `resizeForClassification()` is exported and reused by `detectItems()` too.

### Extra reference angles on an item

A wardrobe item can carry additional photos (back, side, detail, care tag) added from `/closet/[id]` after upload. They live in their own table, `wardrobe_item_photos`, **not** in more image columns on `wardrobe_items`. Outfit styling never treats those rows as separate pieces: renderers read the one selected item image through `wardrobeItemImage()`, while photo enhancement is the only flow that reads reference rows as identity evidence.

`src/app/(dashboard)/closet/[id]/item-photos.tsx` owns the left-hand image column: the big frame (which shows whichever thumbnail is selected — view state only), the strip of main photo + extra angles + add tile, per-photo delete, and an optional free-text `angle` label on the selected photo. Uploads go straight from the browser to Storage and insert rows, then all newly-added rows are analyzed together through `/api/ai/items/[id]/references/analyze`; they do not rerun item detection, background removal, or the main item classifier. HEIC is still converted first via the shared `convertIfNeeded()` in `src/lib/images/convert-heic.ts`. Failure handling runs both ways: a Storage object whose row insert fails is removed, and a delete drops the row before the object, since an orphaned object is invisible while a row pointing at a deleted object renders broken. Capped at `MAX_EXTRA_PHOTOS` (8).

### On-demand item photo enhancement

Closet cards and `/closet/[id]` expose a magic-wand action backed by `POST /api/ai/items/[id]/enhance`. It uses the cost-oriented `bytedance/seedream/v5/lite/edit` endpoint once, with the original as Figure 1 and at most four non-label reference photos. `src/lib/ai/enhance-item.ts` owns the identity-lock prompt and the post-process: BiRefNet removes the generated studio background, then Sharp trims the alpha bounds and fits the piece into a category-specific box on a 1024x1024 transparent canvas. The model improves hanger/lay/perspective/light; deterministic code, not the model, owns equal visual scale and padding.

Reference photos are analyzed once in a single Haiku call and cached on `wardrobe_item_photos.kind/analysis/analyzed_at`. A `label` photo is never sent to Seedream: it only extracts readable brand and fiber composition, which update `wardrobe_items.brand/material`. Existing untyped photos are analyzed lazily on the first enhancement; newly uploaded photos are analyzed as one batch. The common 2–4-photo case therefore costs one small cached vision call plus one Seedream edit and one BiRefNet cutout per enhancement.

Generated output never overwrites `clean_url`. It lands in `enhancement_candidate_url` and the UI requires a Before/After confirmation; accepting promotes it to `optimized_url`, rejecting deletes the candidate, and Restore clears the accepted image. All wardrobe renderers go through `wardrobeItemImage()` (`optimized_url ?? clean_url ?? original_url`), so Closet, Looks, daily/weekly plans, AI Stylist, and the human stylist console agree. The original remains recoverable. The `WARDROBE ITEM PHOTO ENHANCEMENT` block in `supabase/schema.sql` is required before using this flow.

### User-authored item identity and notes

`wardrobe_items.display_name` is the user's authoritative detailed/product name (for example, "The Grove XXIII Golf Course M Jordan"); `user_notes` carries fit, size, provenance, comfort, and wearing constraints. Both are edited on `/closet/[id]`. `src/lib/wardrobe/item-label.ts` is the shared display fallback: use `display_name` verbatim when present, otherwise fall back to the AI subcategory/category metadata. Closet cards, all shared Canvas/picker surfaces, daily/weekly plan lists, and stylist-review comparisons use this helper, and their searches also include both fields. Daily, weekly, and AI Stylist prompts send `name` and `userNotes`, explicitly treating them as authoritative. Do not replace a populated detailed name with a generated generic label.

### Recommended Looks on an item

`/closet/[id]` reads `outfit_items` for the item, then fetches the three newest owning `outfits` with all their item joins. `item-outfits.tsx` renders these through the shared read-only `OutfitCollage`; clicking a card links to `/outfits?open=<id>`, which `outfits-view.tsx` consumes once to open the existing Canvas editor and then removes from the URL. Plans and journal rows are deliberately not treated as saved Looks.

When there are no saved Looks containing the item, the empty state offers an explicit `Generate 3 looks` action. Page load never calls AI. The click calls `POST /api/ai/item-outfits`, which rechecks ownership and emptiness, forces one Haiku tool response containing exactly three distinct complete looks around the target item, validates all IDs plus composition and coverage in TypeScript, then persists ordinary `outfits(ai_generated=true)` and `outfit_items` rows. A failed batch deletes any parents already created. Generated cards therefore survive refresh and open in the normal editor. This feature adds no schema.

HEIC photos (iPhone default) are not natively viewable/processable, so `POST /api/ai/convert` (`src/app/api/ai/convert/route.ts`) converts HEIC→JPEG via `heic-convert` + Sharp resize *before* the client kicks off the classify pipeline above — this must happen client-side prior to upload, not inside `/api/ai/classify`.

Model choice is deliberately Haiku (not Sonnet) for classify, stylist, and the item-count check, to keep cost down; see `checklist.md` cost table before changing models.

### AI Stylist

`POST /api/ai/stylist` (`src/app/api/ai/stylist/route.ts`) fetches the user's full active (`archived = false`) wardrobe and profile and accepts the client-maintained conversation history, not only the latest sentence. Its response contract has two explicit states: `{ type: "question" }` asks at most two focused discovery questions when occasion/impression/practical constraints are still missing; `{ type: "recommendation" }` contains a wardrobe-only item ID list plus summary/reasoning/styling notes. The contract is enforced with a named Anthropic tool and forced `tool_choice`, not prompt-only JSON formatting — Haiku once returned a perfectly useful plain-text follow-up despite the old `FINAL:{...}` instruction, which the route misclassified as an unparseable 502. A final plain-text fallback still returns that text as a normal question response if a provider regression ever skips the forced tool. Returned IDs are validated against the fetched rows before their real images are sent to the client, so a hallucinated ID cannot become a Canvas item.

`src/app/(dashboard)/stylist/page.tsx` renders a structured recommendation as an `OutfitCollage`, opens the shared `ClosetPicker` + `OutfitCanvas` for editing, and saves the edited z-order/`x/y/width` into ordinary `outfits`/`outfit_items` rows (`ai_generated=true`). A saved result remains editable; saving again updates the same Look rather than silently creating a duplicate.

The same page owns the Human Stylist booking entry point. `GET/POST /api/stylist/bookings` generates the offered schedule in the stylist's fixed IANA timezone (`STYLIST_TIME_ZONE`, default `America/New_York`) and converts those same instants into the browser-detected timezone for display (30-minute online slots on weekdays; 9–5 in-person days on Tue/Thu/Sat). It excludes globally occupied intervals, revalidates the chosen slot on POST, and inserts via the service-role client. `stylist_bookings` permits users to read only their own rows; it has no client write policy, so a browser cannot bypass the offered schedule. Its PostgreSQL exclusion constraint is the final race guard against any two confirmed intervals overlapping. This is currently one shared stylist-capacity calendar; staff assignment, payment, cancellation/rescheduling and invitation delivery are separate follow-ups.

### Outfit builder

`/outfits` is split between a Server Component data loader (`src/app/(dashboard)/outfits/page.tsx`) and the interactive Client Component (`outfits-view.tsx`). The page fetches the user's saved outfits with joined `outfit_items`/wardrobe previews and all active wardrobe items in parallel. The client renders both the saved-look library and the create flow.

The builder's left-hand Closet is an available-item pool with category filters and text search. Items are square `object-contain` thumbnails; adding one by click or HTML drag removes it from the pool, and removing it from the Canvas returns it. Do not reintroduce selected items into both places at once. The Canvas is freeform rather than a CSS grid: each selected item has client-side normalized `{ x, y, width }` layout state, can be moved with pointer events (mouse or touch), is brought to the top when manipulated, and is resized from its bottom-right handle. Movement and the 15%–60% width range are clamped to the Canvas bounds. A Closet drag uses the drop coordinates as the initial position; click-add uses staggered defaults.

Canvas items deliberately render `clean_url` first (falling back to `original_url`) without a card background, gray border, label footer, or opaque wrapper, so background-removed wardrobe images read as a collage. Delete/resize controls appear as overlays. Keep the transparent presentation separate from the left-hand Closet cards, which retain their square thumbnail treatment.

Saving requires at least two items. It inserts `outfits` metadata (name, folder/collection, notes, `ai_generated: false`) and then inserts `outfit_items` in current z/layer order with `position` plus normalized `x/y/width`; if the junction insert fails, the newly-created outfit is deleted as rollback. Saved cards can reopen the same geometry for editing or delete the Look (the junction rows cascade, wardrobe items remain). Geometry is shared with `/home` and `/stylist`, so do not encode layout into `position`.

### Data model

`supabase/schema.sql` is the source of truth for the DB; `src/types/database.ts` are the hand-maintained TS mirrors — keep both in sync when changing schema. Nineteen tables: the original nine (`profiles`, `wardrobe_items`, `outfits`, `outfit_items`, `outfit_journal`, `folders`, `style_dna`, `travel_plans`, `preference_swipes`), the Phase 6.0 tables (`google_connections`, `calendar_events`, `outfit_plans`), the Phase 6.1 segment tables (`outfit_plan_segments`, `outfit_plan_segment_items`), `stylist_bookings`, `wardrobe_item_photos`, and the Phase 10-A tables (`stylist_reviews`, `stylist_review_items`, `wardrobe_access_log`). An `outfit_plans` row is one local date per travel scope — `source` records how it was produced but is **not** part of its identity (see "Weekly planning"); ordered child segments hold labels/reasoning/event refs and the segment-item junction holds the complete ordered wardrobe set. `travel_plans` was schema-only until Phase 6.3 and section 21 gave it the columns travel mode actually needs; note that its `daily_outfits`/`weather_data` columns stay unused and no row anywhere has `outfit_plans.source = 'travel'`, because a trip's days are ordinary dated plans — see "Travel mode". Most tables use Supabase RLS keyed on `auth.uid() = user_id` (or an ownership join for junction/child rows). **Exception: `google_connections` has RLS enabled with *no* policy** — this is deliberate, so the client is denied entirely and only the service role ever touches OAuth tokens. `stylist_bookings` is user-readable but server-write-only because availability must consider other users' occupied intervals without exposing those bookings. `stylist_reviews`/`stylist_review_items` are readable by both the client and the stylist who wrote them and writable by neither — see "The human stylist console" — and the same section explains why five tables carry an *extra* `stylist_can_view()` SELECT policy while the rest deliberately do not. Storage RLS on the `wardrobe` bucket scopes objects by the user's folder but also has a public-read policy because item image URLs are served directly.

`src/types/database.ts` contains the hand-maintained mirrors for all Phase 6.0/6.1 planning rows plus `HumanStylistBooking`; the client/API response contract for discovery, visual looks and slots lives separately in `src/types/stylist.ts`.

`outfit_plan_segment_items` carries `x/y/width` with the same meaning as `outfit_items` — normalized Canvas geometry, null until a human arranges the segment. Section 15d's `apply_plan_segment_items()` is the single writer every path funnels through, and it exists for three reasons that are each easy to get wrong: `(segment_id, position)` is unique and **not** deferrable so renumbering in place can transiently collide (surviving rows are parked at `+1000` first); ownership is enforced by joining `wardrobe_items` on the caller's id so a foreign id simply fails to join and trips the count check; and **only an explicit Canvas save rewrites geometry** — regenerating or confirming a segment must not silently discard an arrangement. `save_outfit_plan_segment` copies that geometry into `outfit_items`, so a segment saved to Looks reopens in `/outfits` as the same collage.

`/home` and `/plan` also reuse Saved Looks through that shared segment Canvas. `outfit_plan_segments.saved_outfit_id` means the segment is still an exact saved snapshot; section 20's separate `source_outfit_id` retains which Look an edited segment started from after the exact link is cleared. Canvas Done only persists the plan. A later Save calls `save_outfit_plan_segment_choice()` and, when a source exists, the UI explicitly asks to update that Look or save a new one. AI segment regeneration clears both ids because a newly generated result is no longer an edit of the source Look.

When adding a schema change, update it in `supabase/schema.sql` and apply it yourself — there is no migration tooling in this repo and no `supabase/migrations/` directory. Two ways to apply, and the second is preferred because it can be scripted and verified in the same session: the Supabase SQL Editor, or `npx supabase db query --linked --project-ref <ref> -f <section>.sql`, which runs the SQL over the Management API without Docker, without `supabase link` writing anything into the repo, and without introducing migration files. That path needs `npx supabase login` run once **in a real TTY** — a non-TTY shell (including Claude Code's `!` prefix) fails with `LegacyLoginMissingTokenError`, and the stored credential is per-user, so a later non-interactive call picks it up. Either way, extract the section you are applying rather than re-running the whole file. Existing databases run the re-runnable section 15 planning block, section 16 Human Stylist booking block, section 17 item-photos block, section 18 stylist-review block, section 19 rotation-limits block (`profiles.rotation_limits`), section 20 Saved-Look reuse block, and section 21 travel block (`travel_plans` columns + the two-argument `replace_weekly_plans`) as applicable; a fresh database runs the whole file. **Section 21b replaces `replace_weekly_plans` with a two-argument version and drops the one-argument one first** — leaving both would make every `rpc("replace_weekly_plans", …)` call ambiguous between overloads, which PostgREST reports as a 300 rather than as anything legible; it is also what `/plan` persists through, so 21 without 21b breaks weekly planning rather than only travel. Two things about applying these by hand, both learned the hard way on section 21. **Copy from `supabase/schema.sql` itself**, not from anywhere the text has been re-rendered — a paste arriving with characters silently dropped produced `alter table public.t exists trip_typetext` from a correct one-line statement, and the resulting syntax error points at text that reads fine wherever you copied it from. Section 21 keeps every statement on one line partly so that damage is visible on sight; keep new ones that way. **Run each section as its own submission**: the editor wraps a submission in one transaction, so a later failure silently rolls back the statements that already succeeded — which is how section 21 could report "constraint already exists" and then be entirely absent from `pg_constraint` a minute later. This is equally true of `db query`, so pass one section per `-f`, and **confirm what landed with a second query against `information_schema` / `pg_constraint` / `pg_proc`** rather than trusting the empty success response. A missing block surfaces at runtime as PostgREST `PGRST205` ("Could not find the table … in the schema cache") from the browser client, not as a build failure — the code type-checks fine against a table that doesn't exist yet.

## Doc maintenance (keep these files in sync with the code)

After making a change, update the matching doc **in the same working session** — don't leave it for later. This repo has no migration tooling and no test suite, so these docs are the only record of intent and state; a stale doc is worse than none.

Route the update by *what kind of change it was*:

| If the change is… | Update… |
|---|---|
| Architecture, code layout, a new/renamed route or module, a pipeline behavior change | `CLAUDE.md` (this file) |
| A feature reaching "done", or a bug fixed (root cause + fix) | `checklist.md` (feature-status table and/or Debug Log) |
| A plan, priority, or technical design for unbuilt work | `Roadmap.md` |
| Setup, environment variables, or deployment steps | `README.md` |

`AGENTS.md` is a thin pointer to this file — never copy content into it; it needs no per-change update.

Scope, so this stays signal not noise:
- **Update on**: meaningful changes to architecture, feature status, plans, or setup — the things above.
- **Skip for**: styling tweaks, variable renames, comment edits, and other changes that don't alter behavior, status, or plan. Not every commit needs a doc edit.
- When code and a doc disagree, the code is truth — fix the doc, and note the correction if it was a documented decision.
